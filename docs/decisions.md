## D-001

### 入口リンクは運営が選んで手渡しする（一柳による自動発行はしない）

**決定**: 2026-08-26 / kaz

**検討した選択肢**
| 案 | 内容 |
|---|---|
| **採用** | 運営が個別に発行して手渡す |
| 不採用 | 案件に1回参加した人に一柳が自動発行する |
| 不採用 | 登録完了時に全員へ自動発行する |

**理由**: 構想メモ §2-2「招待権は運営がコントロールする」を優先した。
立ち上げ期は10人程度への配布で足りるため、自動化する必要がまだない。

**引き受けたトレードオフ**
構想メモ §7 の自己増殖ループ（本人が友達を連れてくる）が、**運営の配布ペースに律速される**。
拡大速度の上限は「運営が何人にリンクを配れるか」で決まる。

**影響**
- `invite_tokens.owner_member_id` はそのまま使う。**発行のトリガーが手動になるだけ**でスキーマは変わらない
- 運用側に「入口リンクの配り先の見直し」が定期タスクとして発生する（週次に追加）
- 誰に配るかの人選が、そのままコミュニティの質になる

**覆すコスト: 小**
発行ポリシーの切り替えだけで、スキーマもフローも変えずに自動発行へ移行できる。
拡大が運営の手作業で頭打ちになったら、そのときに切り替えればよい。

**移行するときの推奨**: 「案件に1回参加した人に自動発行」から始める。
実際に稼いだ人だけが友達を誘える形になり、実体のない拡散を防ぎつつループが回る。
リッチメニューに「友達を誘う」を置いてLIFFで自分のトークンを表示させれば、配布に通数を使わずに済む。

## D-002

### 招待リンクを踏まずに入ってきた人は、登録を依頼し、応じなければ退出させる

**決定**: 2026-08-26 / kaz

**理由**: 名簿の整合性と摩擦の低さの折衷。即退出は直接招待した側と揉めるリスクがあり、
黙認は「全員に紹介者が紐付く」という構想の土台を薄める。

**手順**
```
入室を検知 → 名簿にない → Slackに通知
  1. 一柳から登録を依頼する（プッシュ1通・課金対象）
  2. 猶予期間内に登録 → 在籍を認める
       紹介者は不明のまま（referrer_member_id = null）
       この人には入口リンクを発行しない
  3. 猶予期間を過ぎても応じない → 業務用アカウントから退出させる
  4. 招待した人が分かるなら、その人の素行に記録する
```

> **技術的に強制はできない。** LINEには「メンバーによる招待の禁止」という設定が存在しないため、
> 直接招待そのものは止められない。だからこの決定は「入口を塞ぐ」ではなく
> 「入ってきたあとにどう扱うか」の運用ルールになっている。

**新たに決めることが2つ発生した**
| 項目 | 推奨 | 状態 |
|---|---|---|
| 登録依頼の猶予期間 | 3日 | 未確定 |
| リマインドの回数 | 1回まで（プッシュは課金されるため） | 未確定 |

**覆すコスト: 小**（運用判断のみ。実装は「検知して通知する」で共通）

## D-003

### グループ名は「{地域}{卒年}バイトコミュニティ」

**決定**: 2026-08-26 / kaz

**例**
```
関西28卒バイトコミュニティ
関東28卒バイトコミュニティ
関西28卒バイトコミュニティ #2      ← 500人到達で分割したとき
```

**理由**: 何が流れる場なのかが名前だけで分かる。
構想メモ §3-4 の同意文言「バイト案件を流すグループがあります」とも一致しており、
入る前と入ったあとで期待値がずれない。

**注意点**
社名（AI就活）も一柳もグループ名に出ない。つまり**運営の存在感を名前では担保できない**。
引き抜き対策としての「運営がそこにいる感じ」は、
ノートの固定表示と運営アカウントの発言で作る必要がある（[運用設計 シナリオG](operations.md#シナリオg-引き抜きが疑われる)）。

**覆すコスト: 小**（LINEのグループ名は後から変更できる）

## D-004

### 入口リンクは LIFF 直リンクにする

**決定**: 2026-08-26 / kaz

**形式**: `https://liff.line.me/{LIFF_ID}?t={token}`

**理由**: 用意するものがなく、最速で始められる。

**引き受けたリスク（ここだけ一部不可逆）**
配布済みリンクの**リンク先を後から変更できない**。自社ドメインを噛ませていれば
リダイレクト先を差し替えるだけで済むが、直リンクではそれができない。

**そこから生まれる運用制約**
> ⚠ **LIFFアプリを作り直さないこと。** LIFF ID が変わると、配布済みの入口リンクが**全て死にます**。
> 「作り直したほうが早い」と思う場面が来ても、作り直さずに直してください。

**緩和策**
LIFF ID を固定したまま、**エンドポイントURL（LIFFが開くWebページ）は変更できます。**
登録フローの中身・デザイン・項目はいくらでも差し替えられます。
変えられないのは LIFF ID そのものだけです。

**計測**
クリック数はLIFF起動時にサーバ側で記録します。踏んだが登録せずに離脱した人も取れるため、
入口リンク別の転換率（[SPEC §6](spec.md#6-監視すべき指標)）は問題なく出せます。

**覆すコスト: 中**
後から自社ドメインへ移行する場合、**移行後に配る分から新形式にすればよく**、
既存リンクはリダイレクト先が変わらないので生き続けます。
ただし既存の配布済みリンクは永久にLIFF直リンクのままです。
