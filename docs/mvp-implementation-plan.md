# MVP実装計画

対象: 構想メモ §10 の範囲 —
**入口リンク発行 → 登録（30秒） → グループ招待リンクの自動返信 → 入室検知の通知**

前提となる仕様は [`spec.md`](spec.md)、調査結果は [`line-platform-research.md`](line-platform-research.md)。

---

## 0. この計画の前提

- このリポジトリは**空**である。既存基盤（Supabase / n8n / 既存LIFF）のコードはここには無い。
  実装をこのリポジトリで行うなら、既存基盤への接続情報とスキーマの現況を先に取り込む必要がある。
- **フェーズ0が終わるまでコードを書き始めない。** プロバイダー選定を誤ると全部作り直しになる（調査 §3）。

## フェーズ2: バックエンドAPI

### 実行環境の選択

| 案 | 向き | 判断 |
|---|---|---|
| **Supabase Edge Functions** | webhook署名検証・IDトークン検証・トランザクションを含むロジック | **推奨**。型が付き、テストが書け、DBに近い |
| n8n | 通知の配線、定期実行、外部SaaS連携 | 通知とスケジュール実行に限定して使う |

> 全部を n8n のノードで組むと、署名検証・IDトークン検証・ロールバックのようなロジックがGUIに埋もれて
> テストもレビューもできなくなる。**判断ロジックはコード、配線は n8n** に分けることを推奨する。
> ただし既存基盤の運用が n8n 中心なら、その慣習に合わせる判断もありうる（要 kaz 確認）。

### エンドポイント

| # | エンドポイント | 内容 |
|---|---|---|
| 2-1 | `GET /api/invite/:token` | トークン検証（SPEC §4.4）。紹介者の表示名を返す |
| 2-2 | `POST /api/register` | IDトークン検証 → members 作成 → グループ振り分け → 招待リンクをpush |
| 2-3 | `POST /api/line/webhook` | 署名検証 → イベント振り分け |
| 2-4 | 管理: トークン発行・無効化・一覧 | 最初は Supabase の管理画面直操作でも可 |

### webhook のイベント処理

| イベント | 処理 |
|---|---|
| `follow` | 挨拶＋未登録なら登録LIFFへの案内（**reply・無料**） |
| `unfollow` | `members.status='left'` |
| `message`（1対1） | 応募キーワードの受付。**reply で返す**（無料化・調査 §1） |
| `message`（グループ/ルーム） | **記録のみ、返信しない**（SPEC §4.6） |
| `memberJoined` | 名簿照合 → 未登録なら運営通知。歓迎＋ルール掲示を reply（無料） |
| `memberLeft` | `state='left'`、`member_count` 再計算 |
| `join`（botがグループに追加された） | `line_groups.line_group_id` を埋める |
| `leave` | グループを `status='closed'` |

**受け入れ条件**
- 署名が不正な webhook を 400 で拒否する
- グループ内で発言しても bot が一切返信しない（`memberJoined` の歓迎を除く）
- 同じ webhook を2回受けても二重登録が起きない（LINEは再送しうる）

## フェーズ5: 手動運用の型づくり（コード外）

MVPの範囲では**グループ投稿は手動で回す**（構想メモ §10）。ここで型を固めてから自動化する。

| # | やること |
|---|---|
| 5-1 | **業務用アカウントで**最初のグループを作成 → 一柳を招待 → 招待URLを台帳に登録 → 運営2人以上が常駐 |
| 5-2 | ルールをノート/固定表示に掲示（勧誘・営業の禁止） |
| 5-3 | **最初の10投稿は運営メンバーが必ずリアクションを付ける**（構想メモ §7。botはリアクション不可） |
| 5-4 | 投稿のたびに `group_broadcasts` に手動で記録する（通数を追うため） |
| 5-5 | 案件投稿のテンプレを固める（金額は書かない／応募は1対1へ／キーワード返信で無料化） |

## 実装順序と依存関係

```
フェーズ0（判断・設定）
  └─ 0-4 userId一致テスト  ←── ここが通るまで先に進まない
        │
        ├─ フェーズ1（DB）
        │     └─ フェーズ2（API・webhook）
        │           ├─ フェーズ3（LIFF）
        │           └─ フェーズ4（通知）
        │
        └─ フェーズ5（手動運用の型づくり）  ※フェーズ1以降と並行可
```

**最短で価値が出る順**: 0 → 1 → 2-3(webhook) → 5(手動でグループ開始) → 2-1/2-2 → 3 → 4
webhook と手動運用を先に立てれば、**登録LIFFが未完成でも手動招待でコミュニティを開始できる**。
入室検知だけ先に動かしておけば、その間の入室者も記録に残る。

## 後付けフェーズ（MVP後）

| 優先 | 機能 | 前提 |
|---|---|---|
| 高 | グループ自動投稿（案件・実績・残枠） | 手動運用で型が固まってから。通数ルール（SPEC §5）の決定後 |
| 高 | 通数ダッシュボード | `group_broadcasts` にデータが溜まってから |
| 中 | 定期棚卸し（`getGroupMemberIds`） | **認証済みアカウントの取得が前提** |
| 中 | 紹介者スコアの集計とティア変動 | 運用データが溜まってから。既存 `payout_rates` の tier に接続 |
| 中 | 紹介料の計算と支払い | **法的建付けの確定が前提**（構想メモ §8-5） |
| 低 | 属性を絞った個別配信（構想メモ §5 の二段構え） | 既存の属性配信の仕組みを流用 |
| 低 | 管理画面（トークン発行UI） | 最初は Supabase の管理画面直操作で足りる |

## リスクと対処

| リスク | 影響 | 対処 |
|---|---|---|
| プロバイダーを間違える | **致命的**。作り直し | フェーズ0-4 で実データ確認してから進む |
| グループ招待リンクの流出 | そのグループだけ汚染 | LINEアプリで作り直し → 台帳更新。学年×地域の分割が被害を1グループに閉じ込める |
| 未登録入室が多発 | 例外処理では足りなくなる | `group_join_events` の `unknown_notified` 件数を監視。閾値超えたら方針の見直し |
| 通数の想定外の膨張 | 請求が跳ねる | `group_broadcasts` の月次集計＋アラート閾値（SPEC §5） |
| webhookの取りこぼし | 名簿がずれる | `member_count` は毎回再計算（SPEC §4.7）。認証取得後は定期棚卸しで補正 |
| 卒業年度の誤判定 | 案件のミスマッチ | 確認画面で本人に見せて直させる（SPEC §4.3） |
| グループ管理者が担当者の私物LINEだった | **復旧不可**。招待リンク発行権と強制退出権を失う | 業務用アカウントを2つ以上、全グループに常駐させる（運用設計 §0） |
| 法的建付けが未確定のまま紹介料を払う | 法的リスク | 確定まで支払いを開始しない。記録は取り続けて後から遡って支払う（A6） |
