## 1. 【重要】グループ投稿の通数カウント — §8-3 の答え

### 結論: **メンバー人数分カウントされる。1通ではない。**

> メッセージ通数は、メッセージの送信対象となった**人数**でカウントされます。
> 1回のリクエストで指定したメッセージオブジェクトの件数は、メッセージ通数には影響しません。
> グループトークに送信した場合、グループに参加しているユーザー数の分カウントされる。
> 例: 40名が参加しているグループに15回メッセージを送信 → 15回 × 40名 = **600通**

出典: [今さら聞けない！ Messaging APIの通数カウント方法 | LINE Developers](https://developers.line.biz/ja/tips/2026/05/28/how-to-count-messages/) / [メッセージを送信する | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/sending-messages/)
検証: 検索経由で公式記事の内容を確認（原典に直接アクセスできず）**[要再確認]**

### 構想への影響

構想メモ §8-3 は「1通ならグループ投稿を告知の主役にできる」と書いていたが、**その前提は成立しない**。
ただし「グループ投稿をやめる」という話ではなく、**コストを織り込んだ運用ルールを先に決める**必要がある、ということ。

**カウントされないもの（無料）**

| 種類 | カウント |
|---|---|
| 応答メッセージ（reply / replyToken を使った返信） | **されない** |
| あいさつメッセージ | されない |
| LINEチャット（手動チャット） | されない |
| プッシュ / マルチキャスト / ブロードキャスト | **される（対象人数分）** |

出典: [Messaging APIの料金 | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/pricing/) / [LINE公式アカウントの料金プラン｜LINEヤフー for Business](https://www.lycbiz.com/jp/service/line-official-account/plan/)

### 通数シミュレーション

前提: スタンダードプラン（無料枠 30,000通/月）、追加分3円/通

| フェーズ | グループ構成 | 投稿頻度 | 月間通数 | 超過分 | 月額目安 |
|---|---|---|---|---|---|
| 初期 | 6グループ × 平均250人（1,500人） | 週2回 | 12,000通 | 0 | 15,000円 |
| 中期 | 6グループ × 平均400人（2,400人） | 週3回 | 28,800通 | 0 | 15,000円 |
| 拡大 | 12グループ × 平均400人（4,800人） | 週3回 | 57,600通 | 27,600通 | **約98,000円** |
| 拡大＋ | 12グループ × 平均400人 | 毎日 | 134,400通 | 104,400通 | **約328,000円** |

同じ案件を「対象50人にマルチキャスト」した場合は **50通**。400人グループへの投稿（400通）の **1/8**。

### ここから導かれる設計方針（4件）

1. **休眠メンバーにも毎回課金される。**
   500人グループで実際に反応するのが30人なら、毎投稿470人分が無駄撃ち。
   → 定期棚卸し（§2 の `getGroupMemberIds`）の価値が金額で正当化される。**§8-2 は「認証申請する」に傾く**。

2. **「500人まで詰める」はコスト面では不利。**
   構想メモ §5 は500人上限を分割理由に挙げているが、上限ギリギリまで詰めるほど1投稿あたりのコストが上がる。
   場の活気とのトレードオフとして意識的に決めること。人数ではなく**アクティブ率**でグループ運営を見る。

3. **投稿頻度の上限を運用ルールとして先に決める。**
   「グループあたり週N回まで」を決めないと、投稿が増えた月に請求が跳ねる。
   `group_broadcasts` テーブルに送信時のメンバー数を記録し、月次で通数を監視する（SPEC §4.7）。

4. **§5 の「二段構え」はコスト面でも正しい。**
   絞れる案件は個別配信のほうが桁で安い。グループ投稿は「コミュニティの空気を作るための投資」、
   個別配信は「実際に人を動かすための手段」と役割を分けて考える。

### 追加のコスト設計: 「ユーザーに先に喋らせる」

構想メモ §3-7「詳細・応募は1対1へ」の導線は、**組み方次第で無料にできる**。

- ❌ グループ投稿 → 運営が対象者にプッシュで詳細送信 → **プッシュはカウントされる**
- ✅ グループ投稿に「参加希望の方は一柳に『関西0904希望』と送ってください」と書く
  → ユーザーが一柳に発言 → その `message` イベントの **replyToken で返信 → 無料**

1対1の詳細案内・応募受付をこの形にすると、通数コストはグループ投稿分だけで済む。
**replyToken の制約**: 1つのイベントにつき1回のみ使用可・発行から一定時間で失効・1回で最大5メッセージオブジェクトまで。**[要再確認]**

## 2. `getGroupMemberIds` の利用条件 — §8-2 の材料

### 結論: **認証済みアカウント限定**（旧「プレミアムアカウント」も対象だったが、プレミアムアカウント区分は2026年に廃止）

出典: [ユーザーIDを取得する | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/getting-user-ids/) / [グループトークと複数人トーク | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/group-chats/)
検証: 検索経由で確認 **[要再確認]**

### 認証済みアカウントの申請

| 項目 | 内容 |
|---|---|
| 費用 | 無料 |
| 審査期間 | **5〜10営業日**（申請集中時はさらにかかる） |
| 申請中の運用 | メッセージ配信・リッチメニュー・友だち追加は通常通り継続可能（止める必要なし） |
| その他のメリット | 緑の認証バッジ、LINEアプリ内の公式ディレクトリに掲載され検索・友だち追加が可能に |

出典: [LINE公式アカウントの「認証済アカウント」とは？｜LINEヤフー for Business](https://www.lycbiz.com/jp/service/line-official-account/verified-account/)

### 判断材料

- 審査に5〜10営業日かかるが**申請中も運用は止まらない**ので、**先に申請を出しておくのが合理的**。
  MVP実装と並行して申請すれば、実装完了時には認証が下りている可能性が高い。
- §1 の通数分析により、休眠メンバーの棚卸しは**直接コスト削減につながる**。
  未認証のままだと webhook を取りこぼした分の名簿を後から復元する手段がなく、
  「グループに誰がいるのか分からないまま毎月その人数分を課金され続ける」状態になる。
- ディレクトリ掲載は、紹介制の設計（入口を運営がコントロールする）とはやや逆方向。
  検索から直接来た人をどう扱うかを決めておく必要がある（登録は通るが紹介者なし＝ `referrer_member_id` が null になる）。

**推奨: 申請する。ただし MVP のブロッカーにはしない**（未認証でも `memberJoined` による検知は動く）。

## 3. ユーザーIDのプロバイダースコープ — §8-1 の根拠

### 結論: **ユーザーIDはプロバイダーごとに発行される。同一プロバイダー内の複数チャネルでは同じユーザーIDになる。**

出典: [ユーザーIDを取得する | LINE Developers](https://developers.line.biz/ja/docs/messaging-api/getting-user-ids/) / [LINEミニアプリ開発ノート『プロバイダー・チャネル編』](https://zenn.dev/akkiihs/articles/915ccdb26930bb)
検証: 検索経由で確認 **[要再確認・最重要]**

構想メモ §8-1 の懸念は正しい。具体的には:

- LIFF アプリは **LINEログインチャネル** に紐づく
- 一柳の webhook（`memberJoined` など）は **Messaging API チャネル** から来る
- この2つが**同じプロバイダー配下**にあれば、`liff.getProfile()` の userId と webhook の userId は一致する
- **別プロバイダーだと一致せず、登録者とグループ入室者を照合できない** ＝ 構想の土台が崩れる
- **チャネルのプロバイダーは後から変更できない**

### 必要なアクション（実装の最初の1手）

1. 既存の就活DB（送客管理LINE / LIFF `2010483281-…`）がどのプロバイダーにあるかを LINE Developers コンソールで確認する
   - **コンソールにプロバイダーが1つも表示されない場合**、そのLINEアカウントには権限が無い。
     既存プロバイダーの Admin に招待してもらうか、新規プロバイダーを作るかの判断が要る
2. **同じプロバイダー配下**に以下2チャネルを新規作成する（この2つが互いに同一であることが必須）
   - 一柳の Messaging API チャネル
   - 登録LIFF用の LINEログインチャネル
3. 作成後、テストユーザー1名で「LIFFで取得した userId」と「一柳に発言したときの webhook の userId」が**文字列として一致すること**を実際に確認してから先に進む

> ⚠ ただし、既存の送客管理と userId を共有する必要が本当にあるかは別途検討。
> 共有すると「送客側で稼働している人がコミュニティにも来た」ことが自動で分かる（構想メモ §1 の母集団の入口が活きる）反面、
> 2つのサービスの個人データが同一IDで結合されるので、プライバシーポリシー（§8-4）での説明が必要になる。
> **少なくとも一柳の Messaging API チャネルと登録LIFFの LINEログインチャネルは、必ず同一プロバイダーに置くこと。**

## 4. その他の制約（構想メモ §9 の確認）

| 構想メモの記述 | 確認状況 |
|---|---|
| botはメンバーを退出させられない | 妥当。Messaging API に他メンバーを退出させるAPIは存在しない（bot自身が退出する `leave` のみ）**[要再確認]** |
| 招待リンクの発行・無効化はAPI不可 | 妥当。グループの招待URLはLINEアプリ側の機能で、APIから発行・無効化できない **[要再確認]** |
| 「メンバーによる招待の禁止」設定は存在しない | 妥当。ゆえに「入口を塞ぐ」でなく「入室を検知する」設計は正しい |
| グループ内の発言が全部webhookに届く | 妥当。応答モードとwebhookハンドラの両方で「グループでは黙る」実装が必要（SPEC §4.6） |
| `memberJoined` に replyToken がある | 妥当。かつ**応答メッセージは無料**なので、入室時の歓迎メッセージ・ルール掲示は通数を消費しない |
| 1グループ500人上限 | 妥当。ただし §1 の通り、上限まで詰めることにはコストが伴う |
