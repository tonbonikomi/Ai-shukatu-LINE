## 0. 【重要】運営の個人LINEアカウントが業務インフラになる

構想メモにもSPECにも書かれていないが、**運用上いちばん効いてくる制約**なので先に書く。

LINEの仕様上、以下は**botにはできず、人間の個人アカウントにしかできない**。

| できないこと | なぜ | 誰がやるか |
|---|---|---|
| メンバーを強制退出させる | Messaging APIに他メンバーを退出させるAPIが無い | 運営の個人アカウント |
| グループ招待リンクの発行・作り直し | LINEアプリ側の機能でAPI非対応 | 同上 |
| 投稿にリアクションを付ける | botはリアクション不可（構想メモ §7） | 同上 |
| グループの作成・一柳の招待 | botは自分でグループを作れない | 同上 |

### 帰結: 「グループ管理用の業務アカウント」を用意する

**担当者の私物LINEでグループを作ってはいけない。** その人が辞めた瞬間に、
全グループの招待リンク発行権と強制退出権が失われる。復旧手段は無い。

| やること | 内容 |
|---|---|
| 業務用のLINEアカウントを作る | 業務用の電話番号／端末で。複数人で共有できる状態にする |
| 全グループに**2人以上**の運営を入れる | 1アカウントが凍結・機種変で使えなくなっても運営権が残るように |
| 引き継ぎ手順を決めておく | 担当交代時にグループから抜ける前に後任を入れる |

**この準備をMVPのフェーズ0に入れること。** グループを作ってから気づいても作り直しになる。

## 0.5 グループ名の規則

[D-003](decisions.md#d-003) で確定。

```
関西28卒バイトコミュニティ
関東28卒バイトコミュニティ
関西28卒バイトコミュニティ #2      ← 500人到達で分割したとき
```

**社名も一柳もグループ名に出ません。** つまり運営の存在感を名前では担保できないので、
ノートの固定表示と運営アカウントの発言で作る必要があります（§4 シナリオG）。

## 1. 登場人物と役割

| 役割 | 実体 | やること |
|---|---|---|
| **一柳** | LINE公式アカウント（bot） | 登録受付・グループ招待リンクの送信・入室検知・1対1の応答 |
| **グループ管理者** | 運営の業務用個人LINE ×2名以上 | グループ作成・招待リンク発行・強制退出・リアクション初動 |
| **案件担当** | 運営 | 案件のグループ投稿／個別配信、1対1の応募対応 |
| **アラート当番** | 運営（持ち回り） | Slack通知の確認と一次対応 |
| **通数管理** | 運営（月次担当） | 消費通数の集計と請求予測 |
| **招待したい学生** | コミュニティ参加者 | 入口リンクを友達に配る |

## 2. 平常時のリズム

### 毎日（所要 15〜30分）

1. **Slack の通知チャネルを見る**（当番）
   - 未登録者の入室 → §4 シナリオB
   - トークンの不正使用 → §4 シナリオE
   - グループ定員到達 → §4 シナリオD
   - 振り分け先なし → 該当グループを作るか、「その他」に寄せる
2. **案件を流す**（案件担当。§3 の頻度ルールの範囲内で）
3. **1対1の応募対応** — ここが一番重い。案件1件で応募20人なら20往復

### 毎週

| # | やること | 見るもの |
|---|---|---|
| W-0 | **入口リンクの配り先の見直し** | 自動発行しない方針（[D-001](decisions.md#d-001)）なので、ここが拡大速度そのものになる |
| W-1 | 消費通数の確認 | `group_broadcasts` の週次合計。無料枠のペース配分 |
| W-2 | グループ別アクティブ率 | 投稿へのリアクション数 ÷ メンバー数。休眠グループの発見 |
| W-3 | 未登録入室の件数 | `group_join_events` の `unknown_notified`。増加傾向なら方針見直し |
| W-4 | 入口リンク別の転換率 | どの紹介者が機能しているか。配り先の調整 |
| W-5 | 定期棚卸し（**認証済み取得後**） | `getGroupMemberIds` と名簿の突き合わせ |

### 毎月

| # | やること |
|---|---|
| M-1 | 請求額の確認と翌月の通数予算 |
| M-2 | グループの分割・統合の判断（人数とアクティブ率の両方で見る） |
| M-3 | 紹介者スコアの更新とティア変動（**後付けフェーズ**） |
| M-4 | 素行記録の棚卸し。悪質な紹介者の入口リンクを無効化 |

## 3. 案件を流すときの型

### 3.1 グループか個別かの振り分け

```
案件が決まった
  ├─ 対象が全体の1/3以下に絞れる？
  │    Yes → 個別配信（マルチキャスト）。安く、刺さる
  │    No  → グループ投稿。ただし頻度ルールの範囲内
  └─ 条件のいい案件・限定枠 → グループに流さず対象者だけに個別
       （構想メモ §5「二段構え」）
```

対象50人への個別配信は50通。400人グループへの投稿は400通。**8倍の差**が毎回つく。

### 3.2 グループ投稿のテンプレ

**原則: 金額を書かない。応募は1対1へ。**

```
【9/4(木) 大阪・イベントスタッフ】
・9:00〜18:00
・大阪市内（最寄り: 本町）
・高校生不可 / 当日学生証をご提示いただきます
・残り8枠

参加希望の方は一柳（このアカウント）に
「0904大阪」とだけ送ってください。詳細をお送りします。
```

**キーワードで返信させる形にしている理由は2つある。**

1. **通数が無料になる。** ユーザーの発言に対する応答（reply）はカウントされない。
   運営から一方的にプッシュで詳細を送ると人数分課金される。
2. **興味のある人だけが1対1に来る。** グループの発言量が増えず、通知をミュートされにくい。

### 3.3 投稿直後にやること

- **運営メンバーが👍リアクションを付ける**（最初の10投稿は全員必須。構想メモ §7）
  botはリアクションを付けられないので、ここは人間がやるしかない。真似が広がるまでの初期投資。
- `group_broadcasts` に記録する（自動投稿ができるまでは手動記録。**通数を追うため省略しない**）

### 3.4 1対1に来たあとの流れ

```
ユーザー「0904大阪」
   └─ 一柳が reply で詳細＋金額を返す（無料）
        └─ ユーザー「参加します」
             └─ reply で確定連絡（無料）
                  └─ 既存の送客管理へ登録
```

> **無料なのは「ユーザーの発言に返す」場合だけ。**
> 前日リマインドのように運営から一方的に送るものはプッシュ扱いで課金される。
> リマインドは「本当に必要な案件だけ」「対象者だけ」に絞る。

### 3.5 頻度ルール（SPEC §5 / 数値は未確定）

| 項目 | 案 |
|---|---|
| グループあたりの投稿上限 | 週2回 |
| 月間通数のアラート閾値 | 24,000通（無料枠の80%） |

## 4. 例外が起きたときの手順

### シナリオA: 通常の紹介（手作業ゼロ）

```
運営が学生Aに入口リンクを発行（label:「関西28卒・A」）
  → A が友達Bに転送
  → B がタップ → 一柳を友だち追加 → 30秒登録
  → 一柳が「関西28卒」グループの招待リンクを送信（push 1通）
  → B が入室 → memberJoined で名簿照合OK → 歓迎＋ルール掲示（reply・無料）
  → DB に B.referrer = A が記録される
```
**運営の作業: 入口リンクを発行して渡す、それだけ。** 以降は全自動。

### シナリオB: 未登録者が直接招待されて入ってきた

`memberJoined` で名簿に無い → Slack に通知。**botは退出させられないので人が動く。**

**方針は [D-002](decisions.md#d-002): 登録を依頼し、応じなければ退出させる。**

| 手順 | 対応 |
|---|---|
| 1 | 一柳から「登録をお願いします」と個別に送る（push 1通・課金対象） |
| 2 | 猶予期間内に登録された → 在籍を認める。紹介者は不明のまま（`manual_ok`）。この人には入口リンクを発行しない |
| 3 | 猶予期間を過ぎても応じない → 業務用アカウントからメンバーリストで退出させる（`removed`） |
| 4 | 招待した人が分かるなら、その人の素行に記録する。繰り返すなら入口リンクを無効化 |

> リマインドはプッシュで課金されるので **1回まで**。猶予期間と回数はまだ未確定（推奨: 3日 / 1回）。

**想定頻度は低い。** 招待したい学生は自分の入口リンクを使わないと紹介料にならないため、
直接招待するインセンティブがない（構想メモ §9）。ただし**週次で件数を見る**こと。
増加傾向なら「例外処理で足りる」という前提が崩れているサインなので、方針を見直す。

### シナリオC: グループが定員に近づいた

```
450人でアラート
  → 運営が新グループ「関西28卒バイトコミュニティ #2」を作成
  → 一柳を招待（join イベントで line_group_id が自動で埋まる）
  → 招待URLを発行して台帳に登録 → status='open'
  → 旧グループを status='full' に
  → 以降の登録者は自動的に #2 へ振り分けられる
```
**旧グループは残す。** 既存メンバーを移動させる必要はない。

### シナリオD: グループ招待リンクが流出した

**兆候**: 未登録入室の急増、想定外のメンバー増加

```
1. グループ設定から招待リンクを作り直す（旧リンクが無効になる）
2. 台帳の invite_url を更新し、invite_url_updated_at を記録
3. status を一時的に 'rotating_link' にして、新規振り分けを止める
4. 新リンクを台帳に反映 → status='open' に戻す
5. 流出中に入った未登録者を group_join_events から洗い出して対応
```

**被害はそのグループだけで済む。** 学年×地域で分割してある理由がこれ（構想メモ §5）。
なお、一柳が送る招待リンクは受け取った本人が転送できてしまう（技術的に防げない）。
「あなた専用です」という文言は抑止であって、実効性は `memberJoined` の検知側にある。

### シナリオE: 入口リンクが不正に使われた

大量登録・明らかに属性がでたらめ、など。

```
1. 該当トークンを revoke（既に登録済みの人には影響しない）
2. そのトークン経由の登録者を洗い出して確認
3. 発行先の学生に事情を聞く。悪質なら以降の発行を止める
```

### シナリオF: 態度の悪い人が出た

構想メモ §2 が**唯一排除したい対象**。金目的の参加は許容する。

**検知の入口**
- グループ内での勧誘・営業（ルールで禁止と掲示済み）
- ドタキャン・無断欠勤
- 案件先からのクレーム

**対応**
```
1. members / referrer_scores に記録（conduct_penalty, no_show_count）
2. 業務用アカウントからグループを退出させる
3. members.status = 'banned'
4. 紹介者のスコアに反映 → ティア下降 → 単価が下がる
5. 繰り返す紹介者は入口リンクを revoke（紹介権の停止）
```

**4と5が構想の中核。** 運営が審査するのではなく、
「良い人を連れてくれば単価が上がり、荒らせば紹介権を失う」という
紹介者側の経済合理性に埋め込む（構想メモ §2）。
※ ティア変動は後付けフェーズ。それまでは記録だけ取って手動で判断する。

### シナリオG: 引き抜きが疑われる

LINEではプロフィールからの友だち追加を止められず、DMも見えない（構想メモ §7）。
**検知は原理的にできない前提で、構造で対処する。**

| 対策 | 実務 |
|---|---|
| 肝心な情報をグループに書かない | 金額・詳細・応募先は必ず1対1。個別につながっても得るものがない |
| ルールの掲示 | ノート／固定表示に「勧誘・営業禁止」。`memberJoined` の歓迎メッセージでも毎回伝わる |
| 運営の存在感 | 業務用アカウントがときどき発言する。無人の場に見せない |
| 発覚時 | シナリオF と同じ扱い |

## 5. 立ち上げ期（最初の1ヶ月）

ここだけは人手がかかる。**リアクション文化の初動は自動化できない。**

| 時期 | やること | 目安 |
|---|---|---|
| Week 0 | グループ作成 → 一柳を招待 → ルール掲示 → **運営5人が先に入る** | — |
| Week 1 | 入口リンクを10人程度に配る（既存のタイミー稼働者から選ぶ） | 登録30〜50人 |
| Week 2 | 最初の案件投稿。**運営全員でリアクション**。反応率を測る | 反応率10%が目安 |
| Week 3-4 | 紹介が自然に回り始めるか観察。転換率を見て配り先を広げる | 紹介経由の登録が出るか |

**Week 2 で見るべきこと**: 投稿への反応率。低いなら、案件の質・投稿の書き方・
グループの属性の揃い方のどれかが外している。人数を増やす前にここを直す。

**Week 3-4 で見るべきこと**: 運営が配った入口リンク以外から登録が来るか。
来なければ自己増殖ループ（構想メモ §7）が回っていないので、紹介料の設計を見直す。

## 6. どれくらい人手がかかるか

| 局面 | 工数 | 内訳 |
|---|---|---|
| 立ち上げ期 | 運営3〜5人が毎日触る | リアクション初動、投稿の型づくり、初期メンバーとの関係づくり |
| 定常運用 | 1日15〜30分 | アラート確認＋案件投稿＋1対1対応 |
| 週次 | 30分 | 通数・アクティブ率・転換率の確認 |
| 月次 | 1時間 | 請求確認、グループ再編、スコア更新 |

**一番重いのは1対1の応募対応。** 案件1件で応募20人なら20往復になる。
規模が大きくなったらここがボトルネックになるので、
キーワード受付から確定までのテンプレ自動応答を後付けする余地がある
（reply なので通数は無料のまま）。
