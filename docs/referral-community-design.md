## 0. 用語

- **一柳（いちやなぎ）** … このコミュニティで使う公式LINEアカウント。既存の送客管理用OAとは別物。
- **招待したい学生** … 友達を誘いたいコミュニティ参加者。運営が入口リンクを発行する対象。
  ※資料・文面では「エージェント」「代理店」という語を使わない（kaz指示 2026-08-26）。内部の `partners` テーブルとの関係は SPEC化時に整理する。

## 1. 背景

- タイミーで大量に稼働しており、**リストが継続的に流入してくるアカウントがある**（＝母集団の入口が既にある）
- 送客管理・即払いの基盤（Supabase / n8n / LINE）が本番稼働中（＝人を動かす仕組みが既にある）
- 競合が紹介制LINEグループで就活生コミュニティを運営している
- 足りないのは上記2つをつなぐコミュニティだけ

**避けたい失敗** = ジョブハント型の崩壊。誰でも招待できる状態にすると人は集まるが質が落ちて場が死ぬ。

## 2. 方針（kaz裁定）

1. 金目的の参加は許容する。排除したいのは**態度の悪い人だけ**
2. 招待権は運営がコントロールする（入口リンクの発行・停止を握る）
3. ただし「バイト感覚で友達を誘える」**摩擦の低さは殺さない**（審査なし・30秒）
4. 運用は既存基盤で自動化する（人が張り付かない。承認制OCを却下した理由）

**構造 = 「入口はゆるい・実質は固い」。** 審査を運営がやるのではなく、**紹介した側の経済合理性に埋め込む**。
良い人を連れてくれば単価が上がり、荒らせば紹介権を失う。運営がやるのは検知と例外対応だけ。

## 3. フロー

1. **招待したい学生に、運営から専用リンク（入口リンク）を発行**。無効化も随時可能
2. **友達がタップ → 一柳を友だち追加**（＝実質の関所。以降全員が一柳の友だちになり1対1で連絡が取れる）
3. **登録（30秒）** … 氏名 / ふりがな / 大学 / 学年 / 生年月日 / プライバシーポリシー同意。卒業年度は学年から自動計算
4. **「バイト案件を流すグループがあります。招待してもよろしいですか？」** … 興味がある人だけを通すフィルター＋同意の記録
5. **一柳がグループ招待リンクを自動返信** … 学年・地域から該当グループを自動判定
6. **グループに案件が流れる** … botが自動投稿。**金額は書かない**
7. **詳細・応募は1対1へ** … お金の話は完全に個別

### ⚠ リンクは2種類あり、別物（設計の肝）

| | 誰が持つ | 中身 |
|---|---|---|
| **入口リンク** | 招待したい学生 | 一柳の友だち追加＋登録フォームへの誘導。URLに紹介者IDを埋める |
| **グループ招待リンク** | **一柳のみ** | LINEグループそのものへの参加リンク。登録完了者にだけ自動返信 |

招待する側にグループリンクを直接渡すと、コピペで無制限に転送され誰が入ったか把握できなくなる。
一柳を1本挟むことで、**全員が必ず登録を通り、氏名・属性・紹介者が記録された状態でしかグループに入れない**。

## 4. 年齢の正確性

入口では確認しない（30秒フローを守る）。**「嘘をついても後でわかる」構造**で担保する。
登録画面に添える文言はこの1つだけ:

> 年齢確認が必要な案件があるため、正確にご記入ください。案件参加時に学生証をご提示いただく場合があります。

報酬受け取りには振込口座（名義＝本名）が必要なため、**学生証と口座名義の2接点**で虚偽は後々判明する。
最初にそう伝えておくだけで正直に書く率が上がる、という設計。

## 5. グループの分け方

**学年（卒業年度）× 地域**で分割。理由:

- 1グループ**500人が上限**（どのみち分ける必要がある）
- 招待リンクが流出しても**被害がそのグループだけで済む**
- 属性が揃うと案件のマッチ度が上がり、**通知をミュートされにくい**

| 地域 | 27卒 | 28卒 | 29卒 |
|---|---|---|---|
| 関西 | ● | ● | ● |
| 関東 | ● | ● | ● |
| 名古屋 / 九州 / 東北 / その他 | ○ | ○ | ○ |

**全部を最初から作らない。** 人が集まる地域（●）から立て、500人に近づいたら割る。
地域を1つ増やす作業は「グループを作って入口リンクを配る」だけ＝仕組みの作り直し不要。

**二段構え**: 属性を絞った条件のいい案件は、グループに流さず**対象者だけに個別送信**する。
既存の属性配信（地域・卒年・大学タグで絞り込み）がそのまま使える。グループ＝広く浅く、個別＝狭く深く。

## 6. 作るもの

| 機能 | 中身 |
|---|---|
| 招待トークン | 発行・無効化できるリンク。**既存の `partners.ref_code` は使わない**（恒久・取り消し不可のため要件を満たさない）→ 別テーブルで発行 |
| 登録画面 | LIFF 1枚。5項目＋同意チェック |
| グループ振り分け | 学年・地域から該当グループの招待リンクを自動返信 |
| 入室検知 | `memberJoined` で名簿照合 → 未登録なら運営に通知（**対応は手動**） |
| グループ自動投稿 | 案件告知・参加実績・残枠表示 |
| 紹介者スコア | 出席・ドタキャン・否認・素行を紹介者ごとに集計 → ティア変動 |

大半は既存の仕組みが使える。**実質の作業は既存DBへの紹介者ID・スコア列の追加**。
単価のティア変動は既存の `payout_rates` の tier 機構に乗る。

**支払いは案件ごとに設定。基本は月末払い**、必要な案件だけ ⚡即払いをON（既存の `projects.instant_pay` の切り替えのみ）。

## 7. 運用設計

### 安心感（「みんなやってる」）

- **リアクション文化** … 案件投稿には必ずリアクションを付ける。LINEのリアクションは**通知が飛ばない**ので押すハードルが低い。
  ただし**botはリアクションを付けられない**ため、最初の10投稿を運営メンバーで徹底 → 真似が広がるのを待つ
- **実データの見える化** … 「今週は12人が参加しました」「残り3枠」をbotが自動投稿。既存DBから生成可能
- ⚠ **偽の実績・サクラの数字は絶対にやらない**（ばれた時点でコミュニティごと死ぬ・法的にも危険）

### 引き抜き対策

LINEではプロフィールからの友だち追加を止められず、DMも見えない。**「禁止する」より「一柳経由が一番得な構造にする」**。

- **肝心な情報はグループに書かない** … 案件の詳細・応募は必ず1対1へ。個別につながっても得るものがない状態にする
- **ルール掲示と運営の存在感** … 「グループ内での勧誘・営業は禁止」を固定表示。運営アカウントがときどき発言する
- **違反は素行スコアに記録** … 紹介者のティアに響くので紹介者側にも抑止が働く

### 展開性

タイミーからリスト流入 → コミュニティ参加 → 案件で稼ぐ → 紹介料を受け取る → **本人が友達を連れてくる** の自己増殖ループ。
回すほど1人あたりの獲得コストが下がる。全員に紹介者が紐付きスコアが付くため、**増えるほど質の管理が効く**（悪い紹介者は自動的に降格して影響が小さくなる）。

## 8. ⚠ 着手前に決めること（未回答・kaz判断待ち）

1. **LINEのプロバイダをどれにするか** … **後から変更不可**。既存の就活DBと同じプロバイダに置かないと、
   LIFFで取得した userId と `memberJoined` の userId が照合できず**構想の土台が崩れる**。最優先
2. **アカウント認証を申請するか** … `getGroupMemberIds` は**認証済みアカウント限定**。未認証だと
   webhook停止中に入った人を後から棚卸しできない
3. ~~**通数プラン**~~ … ✅ **回答済み（2026-08-26）**: グループ投稿は**メンバー人数分**カウントされる。1通ではない。
   → [調査結果 §1](line-platform-research.md#1-重要グループ投稿の通数カウント--83-の答え)。
   新たに「グループあたりの投稿頻度上限」を運用ルールとして決める必要が出た（[SPEC §5](spec.md#5-通数の運用ルール調査-1-を受けて新規)）
4. **プライバシーポリシーの追記** … 大学・学年・生年月日の取得目的。既存 `/privacy.html` に追記
5. **紹介料の建付け** … 送客成果報酬とは性質が違う（コミュニティ入会への対価）ため弁護士確認。
   利用規約の確認が進行中なので同じタイミングで

## 9. LINEプラットフォームの制約（設計前提）

- **botはメンバーを退出させられない** … 検知は自動だが削除は運営の個人アカウントが手動。
  ただし招待したい学生は自分のリンクを使わないと紹介料にならないため直接招待は稀＝**例外処理で足りる**
- **招待リンクの発行・無効化はAPI不可** … 流出時はグループ設定から手動で作り直す（古いリンクが無効になる）
- **「メンバーによる招待の禁止」という設定は存在しない** … だから入口を塞ぐのでなく**入室を検知する**設計にしてある
- **グループ内の発言が全部webhookに届く** … 自動応答をONにすると誤爆する。**グループでは黙るように作る**
- **`memberJoined` には replyToken がある** … グループ内での自動返信は可能

### 却下した案

- **後追い登録（未登録者に「誰に誘われましたか」を聞く）** … kaz却下「めんどくさい」。
  検知 → 手動対応（例外処理）で足りる、が結論
- **承認制OC（OpenChat）** … bot が入れず自動化できないため却下

## 10. 最初に作る範囲（MVP）

**入口リンク発行 → 登録（30秒） → グループ招待リンクの自動返信 → 入室検知の通知**

ここまでで価値の8割。紹介者の紐付けは初日から全員に記録されるので、**スコア集計とティア変動は運用データが溜まってから後付け**で問題ない。
グループの自動投稿も、最初は手動で回して型が固まってから自動化する方が早い。
